# Client UI Lab

An experimental, 100% client-side Fabric UI library for building desktop-quality Minecraft screens entirely from code.

The default renderer is native and lightweight. It does not start Chromium, load a webpage, parse CSS, or require MCEF. Pages paint into a retained high-quality surface only when their state changes; Minecraft reuses that GPU texture while the UI is idle.

The project currently targets Minecraft 26.2 and Fabric Loader 0.19.3. The name is temporary.

## Showcase

Press `H` from the title screen or in a world. Keys `1` through `5` switch between:

- Discover: a restrained, Modrinth-inspired project browser.
- Loadout: native `ItemStack` and live player rendering inside layout slots.
- Waypoints: a map planner with filters, routes, markers, and controls.
- Performance: telemetry cards, a chart, and the real retained-surface paint count.
- Settings: shape families, buttons, toggles, sliders, and design tokens.

Everything is generated by Java code. There are no bitmap UI assets or AI-generated assets. Loadout uses a safe placeholder on the title screen because Minecraft 26.2 binds item data components when a client world exists; enter a world to render the live player and items.

## Native API

`UiDocument` owns routes, theme tokens, and the shell. Each `UiPage` receives a `UiContext` only when the retained surface needs painting.

A `UiShell` paints whatever chrome sits around the active page and returns the rectangle the page owns. The default is `UiShell.NONE`, which gives the page the entire surface; `UiSidebarShell` is the navigation rail the showcase uses, with every label supplied by the caller. Nothing about the showcase's own design is baked into the renderer, so a consuming mod can build a completely different structure by writing one method.

```java
var page = new UiPage(
    "home",
    "Home",
    "⌂",
    0xFF58A6FF,
    ui -> {
        var g = ui.canvas();
        float x = ui.contentX() + 24;
        float y = ui.contentY() + 24;

        g.textMedium("My mod", x, y, 24, ui.theme().text());
        ui.card(x, y + 48, 260, 100);
        ui.button(
            "save-button", "Save", "save", x + 16, y + 110,
            72, 30, UiContext.ButtonStyle.PRIMARY, UiContext.Shape.ROUNDED
        );

        // DOM-free anchors for native Minecraft rendering:
        ui.nativeSlot("item-slot", x + 190, y + 62, 48, 48);
    }
);

var document = UiDocument.builder("My mod")
    .brand("My mod")
    .theme(UiTheme.dark())          // or UiTheme.light(), or your own tokens
    .shell(UiSidebarShell.create()) // omit for a full-bleed page you paint yourself
    .pageShortcuts(true)            // opt in to keys 1-9 selecting pages
    .page(page)
    .build();

var screen = new UiScreen(
    document,
    nativeLayer -> {
        if (nativeLayer.localPlayer() == null) return;
        nativeLayer.item("item-slot", stack);
    },
    (kind, key, value) -> {
        if (kind.equals("action") && key.equals("save")) saveConfig();
    }
);

Minecraft.getInstance().gui.setScreen(screen);
```

The native library provides:

- Arbitrary code-drawn rectangles, rounded rectangles, circles, paths, lines, text, clipping, and custom icons.
- Cards, four button styles, four shape families, toggles, sliders, hit regions, and state values.
- Per-document theme tokens and per-page accent colors.
- Finite hover, press, navigation, and state animations.
- Native item and entity overlays with skins, enchant glint, durability, and model overrides.
- Pluggable chrome through `UiShell`, so navigation and window framing are not fixed by the library.
- Adaptive desktop-like layout scaling independent from Minecraft's large GUI scale.
- Independently capped supersampling, so small windows stay sharp without oversized fullscreen textures.
- `layoutScale()`, `regionBounds(id)`, and `trackBounds(id)` for anchoring popovers and tooltips to painted controls.

Mods are not limited to the included components. `UiCanvas` is deliberately low-level enough to build entirely different design systems.

### Coordinate spaces

Three spaces are in play, and the distinction matters when mixing native Minecraft rendering into a layout.

- **GUI space** is what Minecraft passes in mouse events and `width`/`height`.
- **Layout space** is what painters draw in. One layout unit is one operating-system point divided by `UiTheme.density()`, so a screen stays the same physical size on a HiDPI display as on a standard one, independent of the player's GUI scale. `UiScreen.layoutScale()` converts between the two.
- **Surface space** is the rasterized texture: layout space supersampled toward the physical framebuffer, then capped.

`nativeSlot` handles the conversion for you, so native items and entities stay aligned across GUI-scale and window changes.

## Performance model

The retained surface is not rebuilt every game frame.

- A static screen paints once, uploads once, and then uses one cached texture blit per Minecraft frame.
- Resize, hover changes, control changes, and mod state changes explicitly invalidate the surface.
- Animations repaint at frame cadence only for their short configured duration, then stop.
- The same `DynamicTexture` and native pixel allocation are reused until the screen size changes.
- Pixel transfer uses one bulk buffer upload instead of allocating a GPU texture for every interaction.
- Raster resolution is capped at 2560×1440-equivalent to prevent runaway memory use.
- Native items and entities use a separate Minecraft render stratum and do not force the retained surface to repaint.
- A theme `motionScale` of `0` removes animation work entirely.

The Performance demo displays the number of surface paints since the screen opened. Once the opening animation finishes, that number stays unchanged until an actual invalidation occurs.

## Optional browser backend

The earlier MCEF renderer has not been deleted. Its document, component, JavaScript bridge, and native-overlay implementation remain in source for a future optional add-on.

The MCEF screen, document, and demo files are excluded from the native source set. The base manifest does not mention MCEF, the build does not download it, the jar does not contain its browser classes, and the default runtime does not load it. The eventual browser add-on can package those preserved sources separately for mods that genuinely need HTML or embedded web content.

## Run and build

```sh
./gradlew runClient
./gradlew runClient -PdemoPage=settings
./gradlew runClient -Pautotest    # dev only: loads a throwaway world, exercises and captures every page
./gradlew build
```

`-Pautotest` runs `DemoAutoTest`, which creates a scratch singleplayer world, walks all five pages, drags the slider and clicks a toggle while asserting the values that come back, opens a second unrelated consumer (`AltShellShowcase`) to prove no showcase styling leaks into the renderer, resizes the window four times, and confirms the surface stops repainting when idle. Screenshots land in `run/screenshots`. It is inert unless the flag is set.

## Before 1.0

The renderer and public API work, but this is not compatibility-stable yet. A public release still needs semantic versioning, a standalone Maven artifact, automated visual regression tests, keyboard-focus and accessibility primitives, and profiling on Windows and Linux GPUs.

Known gaps:

- **No scrolling.** Content taller than its container is clipped. This is the largest missing primitive for real screens.
- **No text input or keyboard focus traversal.** Buttons, toggles, and sliders are mouse-driven only.
- **Action strings are a flat namespace.** `page:`, `toggle:`, and `slider:` prefixes are reserved, so a consumer action must avoid them.
- **Demo pages use fixed vertical offsets** rather than proportional layout, so they leave empty space in unusually tall windows. That is the demo content, not the renderer.
